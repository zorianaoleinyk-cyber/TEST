## Крок 2. Docker і Odoo 19

**Odoo** — програма для керування бізнесом: продажами, складом, бухгалтерією, кадрами та іншими процесами. Її можна розширювати додатковими модулями.
**Docker** — інструмент, який запускає програми в окремих ізольованих середовищах. Це допомагає програмі працювати однаково на різних комп’ютерах.
**Образ Docker** — готовий шаблон із програмою та потрібними для неї файлами й налаштуваннями. Сам по собі образ не виконується.
**Контейнер** — запущений екземпляр образу. Наприклад, із образу Odoo можна запустити контейнер, у якому працює Odoo.
**PostgreSQL** — система керування базами даних. Вона зберігає структуровані дані та дає програмам змогу їх знаходити й змінювати. Odoo використовує PostgreSQL для збереження інформації про бізнес.

## Запит
*потрібно зробити такі дії (перед цим опиши простими словами свій план роботи):*
*1. Встановити Docker на Windows.*
*2. Запустити Odoo 19 Community і PostgreSQL у контейнерах. Налаштування мають лежати файлом `docker-compose.yml` у папці `odoo-test`.*
*3. Створити базу і встановити чотири модулі: **Склад, Продажі, Закупівлі, Виробництво**. Мова інтерфейсу — українська.*

Спочатку Codex пояснив план дій простими словами. Він перевірив, чи встановлений Docker, і повідомив, що команда docker не знайдена. Після цього запропонував встановити Docker Desktop за допомогою команди winget install --id Docker.DockerDesktop --exact --accept-package-agreements --accept-source-agreements і попросив дозвіл на її виконання. Я дозволила встановлення.
Під час подальшої роботи Codex повідомляв про перебіг установлення та перевіряв, чи стала доступною команда Docker. Також він створив у папці проєкту файл docker-compose.yml, у якому описав сервіси Odoo 19 Community і PostgreSQL, а також налаштування для збереження даних.
Після завершення роботи я самостійно відкрила папку D:\TEST\odoo-test і перевірила, що файл docker-compose.yml справді створений. На цьому етапі наявність файлу підтверджена, але запуск Docker і Odoo ще потрібно перевірити окремо.

**Проблема з Docker Desktop**
Після встановлення Docker Desktop під час запуску виникла помилка Virtual Machine Platform is not enabled, а стан Docker Engine відображався як Engine stopped. Через це запустити контейнери за допомогою підготовленого файлу docker-compose.yml поки не вдалося.
Я звернулася до Codex із проханням пояснити причину помилки та перевірити необхідні компоненти Windows і доступність апаратної віртуалізації. Окремо зазначила, що на першому етапі потрібно лише провести діагностику, не змінюючи системних налаштувань, не вмикаючи компоненти Windows і не перезавантажуючи комп’ютер без мого підтвердження.
За результатами діагностики підтримка віртуалізації процесором і відповідний параметр прошивки ввімкнені. Водночас параметр HypervisorPresent мав значення False, тобто Windows не повідомляла про активний гіпервізор.
Виконуваний файл wsl.exe був знайдений, проте отримати інформацію про стан WSL не вдалося через помилку доступу (Access denied). Також не вдалося перевірити стан двох необхідних компонентів Windows — Windows Subsystem for Linux і Virtual Machine Platform, оскільки для цього потрібні адміністративні права.
Codex не вносив змін до системи, не вмикав компоненти Windows і не перезавантажував комп’ютер. Для продовження діагностики він запропонував відкрити PowerShell від імені адміністратора та виконати команди для перевірки стану зазначених компонентів і WSL.
За результатами перевірки компоненти підключені, Codex запропонував перезавантажити ноутбук. Після перезавантаження Docker Desktop запустився коректно. Але потрібно було ще оновлення WSL. Codex запустив wsl --update з адміністративним доступом.
Після оновлення WSL Docker Engine успішно запустився (Engine running). Codex перевірив конфігурацію docker-compose.yml і виявив необхідність додати модуль sale_management для повноцінної роботи продажів. Також було уточнено налаштування спільного тому даних для контейнерів. Після цього Codex запросив дозвіл на завантаження образів Odoo та PostgreSQL і запуск контейнерів.

**Запуск Odoo 19 Community і PostgreSQL у контейнерах, створення бази і встановлення модулів**
Codex запустив завантаження образів Odoo 19 і PostgreSQL та створення контейнерів за допомогою docker-compose.yml. Завантаження відбувалося повільно через великий обсяг даних, але без помилок. Конфігурація передбачає створення бази даних, встановлення необхідних модулів українською мовою та запуск вебінтерфейсу Odoo. 
Після завантаження образів PostgreSQL успішно запустився, а Odoo завершив початкове створення бази даних та встановлення необхідних модулів. За повідомленням Codex, усі 72 необхідні залежності завантажено, а основний контейнер Odoo запущено. Далі перевіряється стан контейнерів і доступність вебінтерфейсу за адресою http://localhost:8069. Codex перевірив роботу Odoo 19: усі чотири модулі — Склад, Продажі, Закупівлі та Виробництво — встановлені, українська мова активна. Docker Engine працює, PostgreSQL доступний, а вебінтерфейс відповідає успішно за адресою http://localhost:8069. Конфігурацію docker-compose.yml оновлено.

**Перевірка**
Для перевірки збереження даних було створено тестовий контакт «Перевірка збереження даних». Після зупинки контейнерів командами docker compose stop та повторного запуску через docker compose start контакт залишився в базі Odoo. Це підтвердило, що дані зберігаються після перезапуску контейнерів.

**Простий сценарій в Odoo**
На наступному етапі потрібно перевірити роботу основних модулів Odoo на прикладі процесу закупівлі сировини, виробництва готового товару та його продажу.
Для цього було визначено послідовність дій:
1. Створити два товари: «Тушка куряча, кг» як сировину та «Філе куряче, кг» як готову продукцію.
2. Закупити у постачальника 100 кг курячих тушок і прийняти їх на склад.
3. Налаштувати специфікацію виробництва та виготовити 45 кг курячого філе.
4. Продати 20 кг готової продукції покупцю й оформити відвантаження.
5. Перевірити фактичні залишки товарів на складі та порівняти їх із розрахунковими.

Для виконання цих дій Codex планує працювати безпосередньо з вебінтерфейсом Odoo. Для цього він запросив дозвіл на керування браузером Opera. Такий доступ потрібен, щоб взаємодіяти з відкритою сторінкою системи, переходити між модулями та виконувати необхідні операції.
Очікуваний результат: після закупівлі 100 кг сировини, виробництва 45 кг філе та продажу 20 кг готової продукції на складі має залишитися 25 кг філе та 0 кг тушок, якщо виробництво використає всю сировину.

Навчальний сценарій виконано в Odoo. Для прикладу створив тестових постачальника й покупця.
Документи:
- Закупівля P00001: 100 кг тушки; надходження WH/IN/00001 прийняте.
- Виробництво WH/MO/00001: за специфікацією 100 кг тушки дають 45 кг філе; замовлення завершене.
- Продаж S00001: 20 кг філе; відвантаження WH/OUT/00001 завершене.
Залишки збігаються з розрахунком: тушки — 0 кг, філе — 25 кг (45 кг вироблено − 20 кг відвантажено).
Різниця між 100 кг сировини та 45 кг філе — 55 кг. У цій навчальній специфікації її не записано як окремі побічні продукти чи відходи, тож Odoo показує її як витрачену у виробництві сировину. 
Ціни були умовні: $10/кг для тушки та $20/кг для філе. Odoo додав податки за стандартними налаштуваннями, тому суми документів відрізняються від простого множення ціни на кількість. Рахунків і оплат не створювалося.

Після виконання сценарію Codex я самостійно повторила основні операції у вебінтерфейсі Odoo 19. AI-помічнику задала запит детальної інструкції щодо виконання простого сценарію самостійно. Створила товари для сировини та готової продукції, оформила закупівлю й приймання 120 кг курячих тушок, налаштувала специфікацію виробництва та виготовила 45 кг філе. Потім оформила продаж і відвантаження 18 кг філе.
Наприкінці перевірила складські залишки: 20 кг курячих тушок і 27 кг філе. Результати відповідали розрахункам.

Під час роботи із системою потрібно перевірити взаємопов’язані процеси закупівлі сировини, її приймання на склад, виробництва готової продукції, продажу та відвантаження. Важливо не лише виконати ці операції, а й переконатися, що вони мають правильні статуси та що складські залишки змінюються відповідно до розрахунків. Наприклад, під час тестування приймання 5 кг товару можна заздалегідь визначити початковий залишок, очікувану кількість після приймання та критерій успіху — збільшення залишку саме на 5 кг і перехід складської операції у статус «Виконано».
На відміну від grill-me та grilling, які допомагають уточнювати умови задачі, ставити запитання й перевіряти логіку рішення, browser-uat-analyst орієнтований на організацію перевірки вже визначеного сценарію. Він допомагає розділити очікувану та фактичну поведінку системи, зафіксувати докази й визначити, чи пов’язана невідповідність із помилкою програми, налаштуваннями або способом проведення тесту. Це робить перевірку послідовнішою та полегшує пояснення отриманих результатів.
Після підтвердження встановлення Codex завантажив скіл у папку C:\Users\User\.codex\skills\browser-uat-analyst. Перша спроба завершилася помилкою WinError 10013 через блокування мережевого з’єднання Windows. Після повторної спроби з підвищеним дозволом скіл було встановлено. Codex перевірив наявність трьох файлів: SKILL.md, README.md і metadata.json.
Під час перевірки також виявлено можливу проблему сумісності: у metadata.json зазначена платформа Scout, а для повноцінного тестування через браузер можуть знадобитися Playwright або сумісний інструмент керування браузером.

*Сценарій тестування.* Було запропоновано перевірити, чи збільшиться складський залишок окремого тестового товару на 5 кг після виконання закупівлі та підтвердження складського надходження. Очікуваний результат: початковий залишок — 0 кг, фактично прийнята кількість — 5 кг, статус надходження — «Виконано», кінцевий залишок — 5 кг.

*Хід роботи*

1. Скіл підготував план перевірки з метою, передумовами, послідовністю кроків, критеріями успіху та можливими причинами розбіжностей.
2. На початку перевірки Codex повідомив, що не змінюватиме базу без окремого підтвердження. Після перевірки середовища було встановлено, що Docker Engine працює, PostgreSQL має статус healthy, а Odoo відкривається в браузері.
3. Після мого підтвердження Codex спробував перейти до створення тестових записів і перевірки складського залишку.
4. У процесі роботи з'ясувалося, що база odoo вже містить навчальні дані: користувачів, контакти, товари, закупівлі, складські переміщення та замовлення на виробництво. У списку товарів були схожі назви, але з різними залишками, тому потрібно було точно визначити, який товар перевіряється.
5. Codex відкрив розділ «Купівлі», однак доступний інструмент керування браузером не дозволив перейти до потрібних дій і перевірити складський залишок. Через це новий тестовий товар і постачальник не були створені, закупівлю не оформлено, а складське надходження не виконано.

*Результат.* Скіл допоміг підготувати структурований тестовий сценарій і визначити, які показники потрібно порівняти. Однак фактичну поведінку Odoo перевірити не вдалося: немає підтверджених початкового й кінцевого залишків для нового тесту, а також завершеного надходження. Тому тест не можна вважати ні успішним, ні проваленим — його виконання заблокувало обмеження керування браузером.

*Висновок.* browser-uat-analyst корисний для планування та документування перевірок вебзастосунку, але його наявність не гарантує, що агент зможе виконати всі дії в інтерфейсі. Для повної перевірки потрібно відновити доступне керування браузером або виконати сценарій вручну.
